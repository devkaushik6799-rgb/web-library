TOPIC 3.1

Introduction to Web Services

Definition: A Web Service is a standardized, self-contained software component exposed over a network (usually HTTP/HTTPS) that enables machine-to-machine communication regardless of programming language, operating system, or hardware platform.

Purpose & Key Characteristics

  • Interoperability: A Python client can invoke a Java or .NET web service seamlessly using open standards (XML/JSON over HTTP).
  • Loose Coupling: Clients depend only on the service contract, not on internal implementation details.
  • Discoverability & Reusability: Services can be published to registries and reused across multiple applications (payment gateways, weather APIs, flight booking).

Advantages & Limitations

Advantages: Cross-platform integration, firewall-friendly HTTP transport, and modular Service-Oriented Architecture (SOA). Limitations: Network latency, XML serialization overhead (in SOAP), and added security surface.

TOPIC 3.2

UDDI (Universal Description, Discovery, and Integration)

Definition: UDDI is an XML-based directory standard that acts as a searchable registry where businesses publish their Web Services and clients discover them dynamically.

Three Components of a UDDI Registry

  • White Pages: Business name, address, contact information, and identifiers.
  • Yellow Pages: Categorization of services by industry, product, or geography (using standard taxonomies).
  • Green Pages: Technical details—binding endpoints, supported protocols, and pointers to WSDL files.

Working Mechanism

1. Publish: Service Provider registers its business entity and WSDL URL in the UDDI registry. 2. Find: Service Requester queries UDDI by category or name to obtain the WSDL location. 3. Bind: Requester reads the WSDL and invokes the provider directly.

TOPIC 3.3

SOAP (Simple Object Access Protocol)

Definition: SOAP is a strict, XML-based messaging protocol for exchanging structured information in decentralized, distributed environments, typically transported over HTTP or SMTP.

SOAP Message Structure

  • <soap:Envelope> (Mandatory): Root element identifying the XML document as a SOAP message.
  • <soap:Header> (Optional): Carries metadata such as authentication tokens, transaction IDs, or routing rules.
  • <soap:Body> (Mandatory): Contains the actual RPC call, parameters, or response payload.
  • <soap:Fault> (Optional, inside Body): Reports error codes and diagnostic messages if processing fails.
soap-request.xml
<?xml version="1.0"?>
<soap:Envelope xmlns:soap="http://www.w3.org/2003/05/soap-envelope">
  <soap:Header>
    <auth:Token xmlns:auth="http://example.edu/auth">XYZ-9912</auth:Token>
  </soap:Header>
  <soap:Body>
    <m:GetStudentResult xmlns:m="http://example.edu/results">
      <m:RollNumber>2026CS101</m:RollNumber>
    </m:GetStudentResult>
  </soap:Body>
</soap:Envelope>

Advantages: Built-in WS-Security, ACID transactions, language/transport independence. Limitations: Verbose XML payloads and higher parsing overhead than REST/JSON.

TOPIC 3.4

WSDL (Web Services Description Language)

Definition: WSDL is an XML-based interface definition language that describes the exact functionality offered by a SOAP web service—what operations exist, what parameters they expect, and the network URL where they can be invoked.

Important WSDL Elements

  • <types>: Defines XML Schema (XSD) data types used in messages.
  • <message>: Abstractly defines input and output data parts for an operation.
  • <portType> (<interface> in WSDL 2.0): Groups abstract operations (like a Java interface).
  • <binding>: Specifies concrete protocol (SOAP over HTTP) and data encoding format.
  • <service>: Associates bindings with physical network endpoint URLs (<port>).
result-service.wsdl (Excerpt)
<definitions name="ResultService" targetNamespace="http://example.edu/results"
             xmlns="http://schemas.xmlsoap.org/wsdl/"
             xmlns:soap="http://schemas.xmlsoap.org/wsdl/soap/">
  <message name="GetResultRequest"><part name="roll" type="xsd:string"/></message>
  <message name="GetResultResponse"><part name="cgpa" type="xsd:float"/></message>
  <portType name="ResultPortType">
    <operation name="GetStudentResult">
      <input message="tns:GetResultRequest"/>
      <output message="tns:GetResultResponse"/>
    </operation>
  </portType>
  <service name="ResultService">
    <port name="ResultPort" binding="tns:ResultSoapBinding">
      <soap:address location="https://example.edu/soap/results"/>
    </port>
  </service>
</definitions>

Web Service Architecture

Definition: Web Service Architecture follows the Service-Oriented Architecture (SOA) triangle comprising three roles—Service Provider, Service Requester, and Service Registry—interacting via Publish, Find, and Bind operations.

Protocol Stack

TOPIC 3.6

Developing and Deploying Web Services

Definition: Developing and Deploying Web Services is the engineering lifecycle of designing a service contract, implementing business logic, packaging the service for an application server, and exposing its endpoint for client consumption.

Two Development Approaches

  • Top-Down (Contract-First): Write the WSDL and XSD first, then generate server stubs and client proxies from the contract (ensures strict interoperability).
  • Bottom-Up (Code-First): Write application classes (e.g., Java JAX-WS or Python/Node handlers) and let the framework auto-generate the WSDL or OpenAPI spec.

Deployment Lifecycle

  1. Define operations and data models.
  2. Implement service logic and exception/fault handling.
  3. Package (e.g., WAR/JAR or Docker container) and deploy to a web/application server (Tomcat, WildFly, Nginx + Node).
  4. Test endpoints with tools like SoapUI, Postman, or curl, then publish WSDL/docs.

TOPIC 3.7

AJAX – Improving Web Page Performance Using AJAX

Definition: AJAX (Asynchronous JavaScript and XML) is a client-side web technique that exchanges small payloads (JSON/XML/HTML) with a server in the background and updates parts of a web page without a full page reload.

Traditional Synchronous Model vs. Asynchronous AJAX

  • Performance Gains: Reduced server bandwidth (no re-sending headers, CSS, or navbars), faster perceived responsiveness, and non-blocking UI.
  • Applications: Live search autocomplete, infinite scrolling, form username availability checks, and real-time dashboards.

TOPIC 3.8

Programming in AJAX

Definition: Programming in AJAX involves initiating asynchronous HTTP calls from JavaScript using either the classic XMLHttpRequest (XHR) object or the modern Promise-based Fetch API, then updating the DOM with the response.

1. Classic XMLHttpRequest & readyState Values

readyState progresses from 0 (UNSENT) → 1 (OPENED) → 2 (HEADERS_RECEIVED) → 3 (LOADING) → 4 (DONE). When readyState === 4 and status === 200, the response is ready.

ajax-xhr.js
const xhr = new XMLHttpRequest();
xhr.open("GET", "/api/notices.json", true); // true = asynchronous
xhr.onreadystatechange = function () {
  if (xhr.readyState === 4 && xhr.status === 200) {
    const notices = JSON.parse(xhr.responseText);
    document.getElementById("notice-box").textContent = notices[0].title;
  }
};
xhr.send();

2. Modern Fetch API with async / await

ajax-fetch.js
async function loadStudentProfile(rollNo) {
  try {
    const response = await fetch(`/api/students/${rollNo}`);
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    const data = await response.json();
    document.getElementById("student-name").textContent = data.name;
  } catch (err) {
    console.error("AJAX error:", err);
  }
}

TOPIC 3.9

CORBA (Common Object Request Broker Architecture)

Definition: CORBA, standardized by the Object Management Group (OMG), is a distributed object middleware architecture that allows objects written in different languages (C++, Java, Python) to invoke methods on each other across a network.

Key Components & Communication

  • ORB (Object Request Broker): The central middleware bus that locates remote objects, marshals parameters, and routes method calls.
  • IDL (Interface Definition Language): Language-neutral syntax defining object interfaces; compiled into client Stubs and server Skeletons.
  • IIOP (Internet Inter-ORB Protocol): Binary TCP/IP protocol enabling ORBs from different vendors to communicate.

Comparison: CORBA vs. Web Services

FeatureCORBAWeb Services (SOAP / REST)
ProtocolBinary IIOP (often blocked by firewalls)Text/JSON/XML over HTTP/HTTPS (firewall-friendly)
Interface DefinitionOMG IDLWSDL (for SOAP) / OpenAPI (for REST)
CouplingTightly coupled distributed object referencesLoosely coupled message/resource exchange
PerformanceVery fast binary serialization on LANsHigher text parsing overhead, scales on the open Web

Unit 3 – Quick Revision & Exam Prep

Important Definitions

  • UDDI: Registry for publishing/discovering Web Services (White, Yellow, Green pages).
  • SOAP: XML messaging protocol (Envelope, Header, Body, Fault).
  • WSDL: XML service contract describing operations and endpoints.
  • CORBA ORB: Middleware routing remote object method calls via IIOP.

Key Differences

  • XHR vs. Fetch API: Callback/event-based vs. modern Promise/async-await.
  • Top-Down vs. Bottom-Up: WSDL-first vs. Code-first service creation.
  • CORBA vs. Web Services: Binary IIOP tight coupling vs. HTTP loose coupling.

Frequently Asked Exam Questions

Q1. What are the three roles in Web Service Architecture?
Service Provider (creates and hosts the service), Service Registry (UDDI directory storing WSDL references), and Service Requester (client discovering and binding to the service).
Q2. What does readyState === 4 and status === 200 signify in XMLHttpRequest?
readyState === 4 means the request is complete and the full response has arrived; status === 200 confirms the HTTP server returned 200 OK.
